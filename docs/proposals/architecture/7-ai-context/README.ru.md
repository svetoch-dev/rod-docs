# REP-7: Модель контекста для ИИ-агентов Svetoch

Русский · [English](README.en.md)

## Overview

Определить модель контекста для ИИ-агентов Svetoch: где находятся знания о платформе, какие правила действуют в репозитории и как агент находит инструкции для конкретной задачи. **AGENTS.md задаёт правила и навигацию, SKILL.md описывает повторяемую операцию**.

Первый клиент — Codex. Агент готовит изменения и запускает проверки; инфраструктуру изменяет существующий CI.

### Current State

Код платформы распределён между bazel-lib, tf-modules и helm-charts. Документация и REPs находятся в rod-docs. Инструкции для ИИ есть в отдельных репозиториях, но общей структуры и порядка обновления нет.

### Problems

- Агент заново разбирает связи между репозиториями.
- Документация может отличаться от используемой версии кода.
- Не определено, где хранить общие правила, ограничения модулей и типовые операции.

## Proposed Solution

Хранить общие правила, карту репозиториев и общие skills в rod-docs. В корневом AGENTS.md каждого рабочего репозитория указать адрес rod-docs с фиксированным тегом и требование читать нужные файлы напрямую. Репозиторные и локальные инструкции держать рядом с кодом. Для специфических или сложных задач с воспроизводимой процедурой использовать skills. Загружать подробности по задаче.

### Desired State

Агент начинает с корневого AGENTS.md рабочего репозитория, переходит по указанному там адресу к общему контексту в rod-docs, затем находит нужный участок кода и читает относящиеся к задаче локальные инструкции и skill.

### Benefits

Общий порядок работы, меньше повторного исследования и лишнего контекста, переиспользование проверенных процедур.

### Trade-offs

Для чтения общего контекста нужен доступ к rod-docs. Новый тег нужно осознанно подключать в каждом репозитории и проверять соответствие используемой версии кода.

## Decision log

**Дата:** 25.10.2026. **Выбранный вариант:** единый источник общего контекста в rod-docs, ссылка на его тег в корневом AGENTS.md каждого репозитория и инструкции рядом с кодом.

Критерии: доступность общего контекста, соответствие версии кода, объём стартового контекста и стоимость сопровождения.

| Вариант | Преимущества | Ограничения |
|---|---|---|
| Все правила и процедуры в одном корневом AGENTS.md каждого репозитория | Простое подключение, всё доступно сразу | Лишний контекст для каждой задачи; общие правила дублируются и расходятся |
| **Ссылка из корневого AGENTS.md на тег общего контекста в rod-docs** | Один источник без копий; каждый репозиторий выбирает версию; подробности читаются по задаче | Нужен доступ к rod-docs; переход на новый тег требует проверки совместимости |
| Фиксированные локальные копии общего контекста | Работа из одного checkout и фиксированная версия текста | Копии нужно обновлять и проверять на совместимость |

**Почему выбран второй вариант:** общие правила и процедуры меняются в одном месте. Корневой AGENTS.md рабочего репозитория даёт агенту точный адрес источника и локальную навигацию. Для поведения модулей агент проверяет используемую версию кода, а не предполагает, что текущая документация ей соответствует.

Тег в AGENTS.md фиксирует версию общего контекста без копирования текста или отдельного файла учёта. Теги rod-docs не переназначаются: для изменения общих правил создают новый тег, а рабочий репозиторий обновляет ссылку после проверки совместимости с используемой версией кода. Сам тег не доказывает совместимость.

## Design Details

### 1. Общий источник контекста

~~~text
rod-docs/
├── AGENTS.md                         # Правила работы в rod-docs
├── docs/ai/
│   ├── README.md                     # Короткий индекс контекста
│   ├── AGENTS.md                     # Общие правила всей платформы
│   ├── repositories.md               # Связи репозиториев и маршруты по задачам
│   ├── terraform.md                  # Контекст для задач Terraform/Bazel
│   ├── gitops.md                     # Контекст для задач Argo CD/Helm
│   └── tooling.md                    # Контекст для инструментов Bazel и образов
└── .agents/skills/<operation>/
    └── SKILL.md                      # Общая процедура отдельной операции
~~~

В общий docs/ai/AGENTS.md включить:

- Проверку версий и чтение кода используемой версии.
- Переиспользование существующих модулей и настроек.
- Размещение данных компании и окружений в конфигурации продукта.
- Запрет на передачу значений secrets, credentials, raw state и plan в контекст ИИ.
- Выполнение apply/deploy через CI; запрет на неявный запуск bootstrap, state-операций и cloud writes агентом.
- Обязательный отчёт об изменениях и выполненных проверках.

В repositories.md описать назначение репозиториев, их зависимости и куда идти для каждого типа изменения. README.md даёт короткий индекс; terraform.md, gitops.md и tooling.md открываются только для задач в соответствующей области. Версии и особенности клиента остаются в рабочем репозитории.

### 2. Контекст рабочего репозитория

~~~text
<repository>/
├── AGENTS.md                         # Назначение, навигация, проверки и адрес общего контекста
└── <module>/AGENTS.md                # Дополнительные правила модуля, если нужны
~~~

Корневой AGENTS.md хранит тег rod-docs и адрес общего контекста, например `https://github.com/svetoch-dev/rod-docs/tree/<rod-docs-tag>/docs/ai/`, где `<rod-docs-tag>` заменяется существующим тегом. Он прямо предписывает прочитать `docs/ai/AGENTS.md` и `docs/ai/repositories.md` из этого тега перед работой, при задаче по Terraform, GitOps или инструментам Bazel открыть соответствующий тематический файл из `docs/ai/`, а при типовой операции найти подходящий `SKILL.md` в `rod-docs/.agents/skills/` по тому же тегу. Ссылка служит навигацией и сама по себе не загружает инструкции в контекст Codex. Общие файлы и skills не копируются в рабочий репозиторий.

Корневой AGENTS.md задаёт порядок: **общие правила из rod-docs → версии зависимостей → инструкции затронутых каталогов → применимый skill → код и проверки**. В нём же остаются назначение репозитория, локальные пути и команды проверок. Вложенные инструкции уточняют правила, но не дают новых полномочий на изменение инфраструктуры. Особенности конкретного репозитория хранятся в его AGENTS.md, README и, при необходимости, собственных skills, которые не дублируют общие процедуры.

При запуске из корня или вложенного каталога агент должен явно прочитать общий источник и применимые локальные файлы. Если rod-docs недоступен, агент сообщает об этом и не выполняет задачу, для которой требуются непрочитанные общие правила или процедуры.

### 3. Область действия локальных инструкций

| Репозиторий | Каталоги | Дополнительные правила |
|---|---|---|
| bazel-lib | tools/, rod/, rod/scripts/init/ | Макросы, генерируемые файлы, Python helpers, побочные эффекты bootstrap |
| tf-modules | modules/rod/, modules/gcp/, modules/yc/ | Defaults, overrides, особенности провайдеров и изменение inputs/outputs |
| tf-modules | Например, modules/gcp/cloudrun_service/ | IAM, secrets, разделение управления конфигурацией и image |
| helm-charts | charts/, charts/chart_deps/app/core/, charts/chart_deps/app/common/ | Переиспользование charts, library/application различия, зависимости и проверки |
| helm-charts | charts/environments/, charts/environment/ | App-of-Apps, paths, revisions, CRDs, ограничения sync/pruning |
| Продукт | Каталоги Terraform, Argo CD и локальных модулей | Пути продукта, окружения, используемые версии и местные особенности |

Локальный AGENTS.md действует для своего каталога и его подкаталогов. Отдельный файл нужен только при дополнительных правилах; он не отменяет общие ограничения безопасности. Описание параметров остаётся в README модуля.

### 4. Сабмодули и версии

- У Git-сабмодуля собственный корневой AGENTS.md, поставляемый с его версией. Перед изменением сабмодуля агент читает его инструкции явно.
- Изменение общей библиотеки оформляется в её репозитории; продукт получает обновлённую зависимость.
- Для сабмодуля использовать gitlink commit, для Bazel и Terraform — фактические refs и версии, определённые по зависимостям. Не подменять их текущим master.
- Общие инструкции и skills читаются из rod-docs по тегу в корневом AGENTS.md. Версии кода берутся из существующих файлов зависимостей. При расхождении инструкции с фактическим интерфейсом используемой версии агент отмечает его и проверяет решение по коду. Обновление общих правил проходит review в rod-docs; переход рабочего репозитория на новый тег проходит отдельную проверку совместимости.

### 5. Skills: процедуры по задаче

Отдельный skill нужен для специфической или сложной задачи, которую можно описать воспроизводимой процедурой: с понятными входными данными, последовательностью действий и проверяемым результатом. Общие skills находятся в rod-docs и читаются оттуда по необходимости; агент не рассчитывает на их автоматическое обнаружение из рабочего репозитория. Уникальные для репозитория skills могут находиться рядом с его кодом. Простая правка, уже объяснённая в README или AGENTS.md, отдельного skill не требует.

~~~text
.agents/skills/<name>/
├── SKILL.md          # Когда применять и как выполнять задачу
├── references/       # Подробности, примеры и особенности репозитория
├── scripts/          # Необязательно: вспомогательные скрипты
└── assets/           # Необязательно: шаблоны и заготовки
~~~

В начале SKILL.md в YAML metadata задаются **name** — идентификатор skill — и **description** — задача и условия применения, по которым агент выбирает процедуру. Основной текст содержит входные данные, необходимые файлы и версии, шаги, ограничения, условия остановки, проверки и ожидаемый результат. SKILL.md объясняет, какие references читать и когда; подробности загружаются по необходимости. Скрипты и шаблоны добавляются только при необходимости.

Создание skill:

1. Определить задачу, условия применения, необходимые данные и признаки успешного результата, опираясь на код и существующий рабочий процесс.
2. Описать действия и проверки; вынести подробности в references/, при необходимости добавить проверенные скрипты и шаблоны.
3. Проверить процедуру на характерной задаче и ошибочных вводных: достаточно ли инструкций, сохраняются ли границы изменений и проверяем ли результат.

Примеры для объяснения наполнения skill, а не обязательный список реализации:

| Задача | Что описать в skill |
|---|---|
| Обновление secrets через Terraform или Argo CD/Kubernetes | Кто управляет ресурсом, где заданы secret или ссылка на него, версия, права и затронутые окружения; как подготовить изменение и проверить его через принятый защищённый процесс, без передачи значения секрета агенту |
| Обновление зависимостей Terraform/Helm | Где фиксируются версии, как проверить совместимость и необходимые миграции, какие связанные файлы обновить и какие проверки выполнить |
| Добавление Cloud Run сервисов | Как выбрать существующий модуль, задать service account, доступ и ресурсы, подключить сервис в нужных окружениях и проверить изменения |

Результат работы — diff и перечень проверок. Агент готовит изменения; инфраструктуру изменяет CI. Значения secrets не входят в контекст. Перед запуском вспомогательного скрипта агент проверяет его действия и побочные эффекты.

### 6. Как формируется контекст задачи

1. Корневой AGENTS.md рабочего репозитория задаёт назначение, локальную навигацию и проверки, а также адрес общего источника в rod-docs.
2. Агент явно открывает общие правила и карту репозиториев из указанного тега rod-docs; тематический файл Terraform, GitOps или Bazel tooling читает только для относящейся к нему задачи.
3. Агент устанавливает версии затронутых зависимостей и читает локальные AGENTS.md по месту изменения.
4. Для повторяемой операции агент открывает подходящий SKILL.md в rod-docs или локальный skill; его references и код читает по необходимости.
5. На основе этого контекста агент готовит изменения и проверки. Неприменимые модули и процедуры не загружаются целиком.

Локальные инструкции меняются вместе с кодом. Общие правила и skills изменяются в rod-docs; рабочие репозитории содержат только указатель на источник и собственные особенности. Несоответствие инструкции фактическому интерфейсу кода отмечается как расхождение; инструкция из более новой версии не применяется автоматически.
